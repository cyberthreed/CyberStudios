### 🌱 make something of your own

Within the permissions granted by each material's license, you can study the source, fork a project, change its behavior, build integrations, redistribute it, or use it commercially.

Keep the copyright and license notices required by the applicable license. Label independently maintained versions clearly so people can tell your fork from an official CyberStudios release. Please don't imply studio endorsement.

These contribution guidelines describe participation in the official project. They do not add restrictions to the freedoms granted by the applicable licenses.

### 🐛 something behaving a little strangely?

For ordinary bugs, open an [issue](https://github.com/cyberthreed/CyberStudios/issues) and include:

- The project name and exact version or commit.
- Your operating system and relevant application version.
- Clear steps to reproduce the problem.
- What you expected and what happened instead.
- Useful error messages, screenshots, or a small example, with private information removed.

Suggestions and constructive criticism are welcome, too. For a large feature or architectural change, start with an issue so we can discuss the idea before you spend time building it.

**For a suspected vulnerability, use the [private security-reporting process](SECURITY.md).** Keep passwords, tokens, API keys, personal data, and exploitable details out of public issues.

### 🛠️ bring a change to the studio

1. Fork the repository and create a branch for your work.
2. Read the documentation for the part you're changing. This repository holds several projects with different tools and requirements.
3. Keep the change focused. Follow the surrounding architecture and code style, and avoid unnecessary dependencies.
4. Check the behavior you changed. Run relevant existing tests or builds where available; for documentation or visual changes, review the instructions, links, or layout as appropriate.
5. Update documentation when a feature, installation step, or behavior changes. If a downloadable package is part of your change, keep it consistent with the source.
6. Open a pull request explaining the problem, your change, how you checked it, and any remaining limits. Add screenshots for visible interface changes when useful.

Small fixes don't need an elaborate proposal. Bigger systems deserve a conversation first. Maintainers decide which contributions belong in the official project; opening a pull request doesn't guarantee acceptance.

### 🎀 keep the official spaces feeling like home

Official CyberStudios interfaces and public writing follow the studio's **Cybercore** identity: baby pink, lavender, powder blue, pearl white, readable text, playful windows, and a little internet nostalgia.

Use the [main README](README.md) as the brand reference. Keep the official tagline exactly as written: **`dream in pixels. create without limits.`** Preserve Cy and Byte's established identity and supplied artwork. Describe real features and tested compatibility accurately.

Independent forks are free to explore their own creative direction under the applicable licenses.

### ⌘ a note for maintainers

The **Protect Main** ruleset targets `main`, blocks force pushes, and restricts branch deletion. Routine direct commits remain available to authorized maintainers. Required pull requests, required status checks, restricted updates, and restricted branch creation are not enabled by this ruleset.

Contributors can continue to use forks and pull requests. Maintainers should review changes, preserve other people's work, and check the result before updating the official branch. CI requirements can be considered once the appropriate checks are configured.

### 🫧 people, privacy & project life

Be constructive and respect the [Code of Conduct](CODE_OF_CONDUCT.md). Disagree with an idea without attacking the person who brought it.

Contributions must not introduce malicious software, hidden surveillance, credential collection, or intentional vulnerabilities. Explain data collection and network activity clearly, and prioritize user privacy.

Projects may be experimental, incomplete, or changing. Support, fixes, feature acceptance, and update schedules are not guaranteed. Read the relevant documentation and license before building on a project.
